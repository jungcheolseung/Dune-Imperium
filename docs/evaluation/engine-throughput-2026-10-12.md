# 학습 엔진 병목 조사 (2026-10-12)

## 후속 구현

사용자 요청 "engine-speed-audit에 체크아웃하고 개선 가능한지 해보자"에 따라 메인 작업 폴더를
그 브랜치로 전환했다. 아래 최초 조사에 이어 실제 엔진과 앱 AI에 두 개선을 적용했다.

- `2b417f51`: `GameState`·`PlayerState`에 선언된 필드에서 `__replace__`를 한 번 생성한다.
  엔진의 복사 호출은 `copy.replace`로 그 경로를 사용한다. 기존 생성자와 모든 불변식 검사·
  `hand_public` 정규화를 유지한다. 새 필드는 자동 포함하며, 알 수 없는 필드·하위 클래스·
  InitVar·init=False·키워드 전용 생성자는 표준 복사로 처리한다. 카드 정의 복사는 표준 경로다.
- `aa355d4a`·`adf6785a`: 생성된 불변 archetype의 속성 목록을 초기화 때 정규화하고,
  카드 ID 파싱과 정적인 카드 Entity 조회를 각각 상한 4,096의 순수 함수 캐시로 재사용한다.
  instance·owner·archetype을 구분한다. 사용자 정의/변경 가능한 archetype은 매번 읽으며,
  현재 catalog에서 정의가 바뀌면 오래된 Entity를 재사용하지 않는다. 평가 점수와 Ability는 캐싱하지 않는다.
- 전체 검사에서 최초 Entity 캐시의 변경 가능한 전역 dict가 앱 AI의 모듈 상태 감사를 어겼다.
  기존 감사 테스트를 유지하고, 기존 앱 AI의 정적 조회와 같은 순수 함수 캐시로 고쳤다.
  동시 실행·모듈 상태·별도 프로세스 감사와 캐시 회귀 11개가 모두 통과했다.
- 표준 복사와 맞대는 회귀 17개, 메타데이터·소유자·변경 가능한 입력·상한 회귀 8개를 더했다.
  기본·CHOAM·전체 옵션의 기준선 저장 3개를 현재 엔진에서 불러와 20단계를 더 진행했고
  기준선과 같은 상태 hash에 닿았다. 이 기기에는 사용자가 둔 `saves/`가 없으므로 기준선으로
  생성한 저장본을 썼다. codec·관측 layout·규칙 판정·보상은 바꾸지 않았다.
- 최종 전체 pytest **7,510 통과·9 skip(7,519 수집)**, Ruff·mypy `src tests` 통과(485파일).
  새 수집 대조 스크립트도 Ruff와 실제 2 worker 실행 스모크를 통과했다.

PlayerState 30.86 → 17.22 μs였다(각 여섯 번의 중앙값,

### 실제 구현의 최종 수집 시간

최종 전체 pytest가 끝난 뒤 다른 측정과 겹치지 않게 셀을 순차 실행했다. 각 조건에서
기준선→새 엔진, 새 엔진→기준선, 기준선→새 엔진 순서로 같은 8판을 세 번씩 수집했다.
아래 숫자는 **벽시계 초**, 비율은 각 짝의 시간 감소율 중앙값이다. 모든 조건의 여섯 셀에서
learner 배열·보상·종료 점수 fingerprint가 일치했고, truncation 0이었다.

| 조건 | 기준선 3회(초) | 새 엔진 3회(초) | 감소 중앙값 |
| --- | --- | --- | ---: |
| self-play, worker 1 | 10.669 · 11.134 · 10.699 | 10.544 · 10.052 · 10.603 | **1.2%** |
| 반은 self-play·반은 앱 AI 상대, worker 1 | 17.796 · 17.702 · 17.504 | 15.236 · 15.860 · 15.225 | **13.0%** |
| 같은 혼합, worker 2(시작·전송 포함) | 15.734 · 15.423 · 15.486 | 14.560 · 13.634 · 13.374 | **11.6%** |

worker 수를 바꾸면 batch와 난수 소비가 달라져 서로 다른 판이 되므로, worker 1과 2의 절대 시간을
직접 나눠 병렬 확장률을 주장하지 않는다. 각 조건 안에서 두 소스만 비교한다.
혼합 수집의 감소율은 각각 10.4–14.4%, 7.5–13.6%였다. self-play는 0.9–9.7%로 편차가 있으며,
이번 실제 Collector 결과로 큰 엔진 전체 개선을 주장할 수 없다.

**결과:** 앱 AI를 섞는 수집에는 12–13% 안팎의 실제 개선을 확인했다. self-play만은 감소가 작았고,
복사 함수의 28–44% 절약이나 최초 임시 실험의 9.3%를 전체 수집의 효과로 옮겨 말하지 않는다.
추가 후보는 관측의 NumPy 변환·기록 비용과 변하지 않은 불변식의 재검사다. 이번에는 적용하지 않았다.
이 기기의 8판·CPU·5081·고정 Leader 측정이므로 최신 Y와 학습 머신의 이미 열린 pool에서 다시 잰다.
학습 갱신·평가·checkpoint 쓰기는 위 수집 시간 밖이다.

원자료는 `tmp/engine-final-selfplay-w1.jsonl`, `tmp/engine-final-mixed-w1.jsonl`,
`tmp/engine-final-mixed-w2.jsonl`이다. worker CPU의 합은 재지 않았다. 병렬 출력의
`coordinator_cpu_seconds`를 전체 core-seconds나 벽시계 절약으로 해석하지 않는다.

## 호출 횟수로 확인한 비용

셀프플레이 8판의 결정 7,032회에 대해:

| `GameState.__post_init__` | 28,922 | 4.11 |
| `PlayerState.__post_init__` | 14,889 | 2.12 |

`GameState`는 필드 70개, `PlayerState`는 84개다. 수를 한 번 두는 동안 여러 중간 상태를 만들고,
그때마다 dataclass의 모든 필드를 모아 생성자를 호출하며 상태 전체의 불변식을 다시 검사한다.
이 복사는 규칙 진행과 합법 여부의 dry run 양쪽에 나타난다.

합법 행동 비용 중 큰 부분은 Agent 효과의 pending group·single box·choice provider다.
`current_agent_effect_context`는 provider마다 같은 frame의 tuple에서 dict를 만들고 필수 키를
확인한다. 단순히 그 dict를 공유하는 캐시는 부적절하다. 호출자가 dict를 바꿔 다음 frame을
만드는 경로가 있으므로, 읽기 전용 표현과 갱신용 복사를 나누는 설계가 먼저 필요하다.
규칙 dry run을 조건식으로 바꾸는 것도 이 조사 범위에서 하지 않았다.

앱 AI 상대 묶음에서는 `Entity.list_attr` 4,022,812회, `card_entity` 1,476,389회,
`card_id` 3,415,312회가 나왔다. 덱 시너지를 평가하면서 같은 카드의 불변 archetype 태그·능력
목록을 매번 문자열 tuple로 바꾸고 카드 Entity를 새로 만드는 비용이다.

## 후보 실험

생산 엔진에는 어느 대체 함수도 적용하지 않았다.

1. **상태 복사의 필드 수집 경로:** `GameState`·`PlayerState`에 한해 필드별 직접 접근으로
   기존 생성자를 호출하는 대체 `dataclasses._replace`를 임시 설치했다. 모든
   `__post_init__` 검사는 그대로다. 실제 구현은 표준 라이브러리 전역 패치 대신 두 상태 타입의
   명시적인 복사 경로로 제한하고, 잘못된 필드·불변식 위반의 거부도 검증해야 한다.
2. **공개 좌석의 인코딩 캐시:** 이미 존재하는 불변 `PublicPlayerView`를 객체 identity와
   관측의 상대 좌석 위치로 키 삼아 공개 좌석 벡터 구간을 재사용한다. 저장한 참조와 `is`로
   identity를 확인하고 4,096항목에서 비운다. 비공개 관측과 GameState 의존 추가 필드는 매번
   생성한다. 프로토타입은 전체 공개 view가 같을 때만 재사용한다.
3. **불변식 검사 비용 분리:** 처음에 두 큰 상태의 `__post_init__`를 비우자 동일 시드의
   관측이 달라졌다. `PlayerState.__post_init__`는 검증뿐 아니라 손패에서 떠난 카드의
   `hand_public` 표시를 지우는 정규화도 한다(같은 파일 386–394행). 첫 차이는 시드
   2,000,000의 357번째 결정 뒤 Reveal 관측에서 이미 공개 손패를 떠난 카드가 남는 것이었다.
   따라서 이 결과는 속도 개선값으로 채택하지 않는다. 따로 그 정규화는 남기고 검사만 끈
   `checks-off`로 비용을 분리했다. 검사를 없애는 것 역시 채택 후보가 아니다.
   실제 개선은 불변식별로 의존하는 필드가 그대로일 때 검증 결과를 재사용하거나,
   불필요한 중간 상태 복사를 합치는 것이다. 정규화는 반드시 유지한다.
4. **앱 AI 고정 메타데이터 캐시:** archetype identity와 속성 이름별 `list_attr` 결과,
   `(instance_id, owner)`별 카드 Entity(상한 4,096)를 재사용한다. 현재 생성 데이터는 불변이다.
   상태에 따른 평가 점수나 변경 가능한 Ability 객체를 캐싱하지 않는다.

채택 후보별 run의 모든 기록된 관측 배열·제시한 합법 catalog indices·선택 행동·좌석·종료 점수를
SHA-256으로 비교하고, 판별 마지막 전체 상태의 canonical hash도 맞댔다.
이것은 측정한 판의 일치를 확인하며, 오류 경로·모든 카드·모든 Leader를 검증한 것이 아니다.

### 탐색 측정

기준선 pytest와 함께 돌린 첫 세 번의 8판 수집이다. 표는 **각 묶음의 벽시계 초**이며,
core-seconds도 마지막 표시 자리까지 거의 같았다. 순서를 정방향·역방향·혼합으로 바꿨다.
각 열의 기준선과 후보 비율을 비교해야 하며, 서로 다른 경로의 절약률을 합하지 않는다.

| 셀프플레이 후보 | 1회 | 2회 | 3회 |
| --- | ---: | ---: | ---: |
| 기준선 | 13.788 | 13.509 | 13.593 |
| 상태 복사의 필드 수집 개선 | 13.009 | 12.728 | 11.618 |
| 공개 좌석 인코딩 캐시 | 14.390 | 13.123 | 14.081 |
| 복사 개선 + 공개 좌석 캐시 | 13.145 | 11.787 | 11.644 |
| 검사만 제거(채택 불가) | 11.070 | 12.587 | 12.328 |

공개 좌석 캐시만은 이 측정에서 이득이 일관되지 않았다. 복사 개선을 우선 검토하고,
최종 후보는 아래처럼 pytest가 끝난 뒤 수집 하나만 실행하는 추가 측정으로 확인했다.
공개 좌석 캐시는 약 28,128호출 중 17,200건(61%)을 재사용했다.

| 망 대 앱 AI 셋 | 1회 | 2회 | 3회 |
| --- | ---: | ---: | ---: |
| 기준선 | 29.693 | 30.942 | 31.620 |
| 고정 메타데이터 캐시 | 24.946 | 25.455 | 26.665 |

앱 AI 캐시는 세 번 모두 같은 관측·합법 행동·선택·최종 상태를 유지했다. **앱 AI 상대 묶음의
수집 시간 16% 안팎 감소**는 이 조건에서의 탐색 결과다. 앱 AI 판단만의 절약률이나
32판·4 worker 학습 전체의 절약률은 아니다. 최신 망·실제 학습 머신에서도 확인해야 한다.

기본 룰셋 시드 2,000,100–2,000,103의 별도 4판도 복사 개선 + 공개 좌석 캐시와 맞댔다.
5.648 → 4.884초, 관측·합법 집합·행동·최종 상태 일치, truncation 0. 한 번의 스모크이므로
이 수치로 기본 룰셋의 평균 개선 폭을 주장하지 않는다.

### 테스트 종료 뒤 단독 수집 재확인

pytest와 앞 A/B가 모두 끝난 뒤, 측정 프로세스 하나로 같은 셀프플레이 8판을 다시 돌렸다.
체크포인트 읽기는 재사용해 측정 밖의 작업을 줄였으며, 정책 표본 난수는 매번 동일하게 새로 만들었다.
벽시계 초와 core-seconds는 0.004초 이내로 일치했다. 모든 run의 관측·합법 집합·행동·
종료 상태가 동일하고 truncation 0이었다.

| 후보 | 1회(초) | 2회(초) | 3회(초) | 열별 시간 감소의 중앙값 |
| --- | ---: | ---: | ---: | ---: |

| 상태 복사 개선(검사 유지) | 9.139 | 9.267 | 9.241 | **9.3%** |

복사 개선은 세 번 모두 빨랐다(6.5–15.4% 시간 감소). 공개 좌석 캐시만은
+5.3%·−5.6%·+2.2%여서 이번 측정으로 일관된 이득을 입증하지 못했다.
둘을 합친 후보가 복사 개선 하나보다 더 낫다는 근거도 없다. 큰 행렬·프로세스 수·
현재 망이 다른 Mac 학습에 이 비율을 그대로 대입하지 않는다.

## 구현 우선순위와 완료 기준

1. **상태 복사부터:** 두 큰 상태 타입에만 빠른 복사 경로를 제공한다. 기존 생성자·정규화·
   모든 불변식 거부를 유지하고, 잘못된 필드·불가능한 병력/카드 존을 거부하는 테스트를 함께 둔다.
   동일 시드의 판별 관측·합법 행동·선택·최종 hash와 실제 저장본을 맞댄 뒤,
   최신 Y의 32판/4 worker 수집에서 판단한다.
2. **앱 AI를 섞는 학습:** 불변 카드 Entity와 archetype 속성의 결과를 유한 크기로 재사용한다.
   사용자 정의/변경 가능한 archetype, owner가 다른 Entity, mutable Ability와 상태별 평가 점수는
   캐시 범위를 구분한다. 앱 AI 정책 자체의 선택이 동일한지 여러 룰셋·Leader로 확인한다.
3. **다음 설계:** 검사별 의존 필드가 같을 때 검증 결과 재사용, 중간 상태 복사 병합을 검토한다.
   `hand_public` 정규화와 초기 생성/저장 불러오기의 전체 검증을 유지한다. context dict 공유와
   규칙 dry run 제거는 별도 설계·규칙 근거 검증이 필요한 작업이다.

공개 좌석 캐시와 worker 수 재측정은 그 뒤에 둔다. 이번 조사로 학습 보상·codec·관측 layout·
규칙 결과를 바꾸는 작업은 채택하지 않았다.

PYTHONPATH=tmp/engine-speed-audit/src .venv/bin/python tmp/quiet_engine_ab.py

`engine-selfplay.prof`·`engine-app.prof`와 `*-profile.txt`, `*-timers.jsonl`,
`engine-speed-ab-v2.jsonl`·`engine-speed-ab-v2.log`, `engine-speed-quiet.jsonl`·`engine-speed-quiet.log`가 출력이다.

순서를 바꿔 세 번씩 실행하고 `time.process_time`의 core-seconds와 벽시계 초를 함께 기록한다.
