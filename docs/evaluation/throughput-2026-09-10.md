# 처리량 회귀 귀인 (2026-09-10)

인수인계의 **④ 처리량 35% 회귀 귀인** 항목을 측정으로 마감한 기록이다. 대상은 두 기준선
리포트가 같은 명령·같은 기계(Apple M4, 8 worker)로 재고, 거의 같은 step 수인데도 어긋난 값이다.

```bash
uv run dune-imperium-tournament --agents heuristic,random,random,random \
    --games 25 --ruleset base --rotate-leaders --workers 8
```

| | [baseline-2026-09-06](baseline-2026-09-06.md) 1절 | [baseline-2026-09-10](baseline-2026-09-10.md) 1절 |
|---|---:|---:|
| duration | 1.7s (59.25 games/s) | 2.6s (**38.71 games/s**) |
| total steps | 63,216 | 64,288 (+1.7%) |
| heuristic ms/decision | 0.005 | 0.010 |
| random ms/decision | 0.001 | 0.006 |

측정 구간은 `c40912f`(09-06 리포트를 넣은 커밋)부터 `cf1530a`(09-10 리포트)까지 **163 커밋**이다.

## 1. 결론

회귀는 실재하고, **step당 엔진 CPU가 약 1.6배가 된 것**이다. 고정 비용(worker 기동·import·pool)도
아니고 에이전트도 아니다. 근거는 아래 2절의 재현이고, 특히 **단일 프로세스에서 더 크게**(1.66배)
재현된다는 점이 pool·import 계열 설명을 전부 배제한다.

원인은 한 곳이 아니라 **엔진이 확장 4종을 담게 되면서 전 구간이 함께 무거워진 것**이다. step당
Python 호출 수라는 결정론적 지표로 **1,218 → 1,849 (1.51배)**이고, 이 비율이 실측 소요 시간 비율
(1.62~1.66배)과 맞는다. 그중 **실제 결함 2건**을 이 세션에서 고쳤고(3절), 나머지는 콘텐츠의
대가다(5절). 앞 세션이 지목한 용의자 `6782c89`는 소수 항이었다(6절).

## 2. 재현 (이 저장소, WSL2/Linux, 8코어, Python 3.14.7)

기계가 달라 절대값은 M4와 다르지만 **비율은 재현된다**. 세 트리를 같은 인터프리터에
`PYTHONPATH`로 물려 직렬로 번갈아 5회(단일 프로세스는 3회) 재고 중앙값을 쓴다.

| 트리 | 8 worker | 단일 프로세스 | heuristic ms/decision (8w) |
|---|---:|---:|---:|
| `c40912f` (09-06 기준선) | 10.10s (9.93 games/s) | 25.50s | 0.029 |
| `2579d60` (이 세션 직전 HEAD) | 16.40s (6.10 games/s) | 42.40s | 0.080 |
| `88c0ef7` (이 세션 수정 후) | **15.50s** (6.47 games/s) | **40.20s** | **0.045** |

- 회귀 재현: 8 worker **1.62배**, 단일 프로세스 **1.66배**. M4의 1.53배와 같은 계열이다.
- 이 세션의 수정: 8 worker **−5.5%**, 단일 프로세스 **−5.2%**. `ms/decision`은 **−44%**.
- step 수는 세 트리 모두 게임 내용대로만 다르고(63,216 / 63,716 / 63,716) 수정 전후는 **완전히
  동일**하다 — 수정으로 달라진 게임이 없다는 뜻이다.

### 측정을 믿을 수 있게 만든 것

- **CPU 경합에 면역인 지표를 먼저 잡았다.** cProfile의 *호출 횟수*는 결정론적이라 다른 작업이
  같은 기계를 쓰고 있어도 정확하다. cProfile의 *누적 시간*은 호출 수에 비례해 부풀기 때문에
  트리 간 비교에 쓸 수 없다(실제로 이 세션에서 한 번 정반대 결론을 냈다).
- 소요 시간 측정은 기계가 조용할 때만, 한 번에 하나씩, 트리를 번갈아 가며 잰다.
- 09-06과 09-10 리포트의 `duration`은 `run_tournament`의 `ProcessPoolExecutor` 블록 전체를 감싸므로
  **worker 기동과 import를 포함한다**. 반면 `ms/decision`은 `_MeteredAgent` 안쪽이라 에이전트
  자신의 시간만 잰다. 두 값의 의미가 다르다는 것이 4절의 열쇠였다.
- 참고: Python 3.14는 Linux 기본 start method를 `forkserver`로 바꿨다(gh-84559). 이 저장소의
  3.14.7도 `forkserver`이므로 macOS(`spawn`)와 마찬가지로 worker마다 import를 다시 치른다.

## 3. 고친 결함 2건

### (a) `ab48e0c` — 에이전트에게 harness 비용을 청구하던 Protocol 검사

`StateAgent`는 `@runtime_checkable` Protocol이라 `isinstance()` 한 번이 멤버를
`inspect.getattr_static`으로 훑는다(이 기계에서 약 **5us**). 이것을 **결정마다** 묻는 자리가
세 곳이었다: runner의 분기, tournament `_MeteredAgent`의 분기(**계측 구간 안**), 학습 수집의
batch policy.

리포트 자체가 이 결함의 지문을 남기고 있었다: heuristic이 0.005 → 0.010, random이 0.001 → 0.006으로
**둘 다 정확히 +0.005 ms**다. `random_agent.py`는 이 구간에서 한 바이트도 바뀌지 않았으므로,
에이전트가 느려진 것이 아니라 **모든 좌석에 같은 상수가 더해진 것**이다.

좌석은 게임 도중 바뀌지 않으므로 이제 좌석당 한 번만 묻는다. 회귀 테스트는 시간이 아니라
불변식이다 — 세는 대역 클래스로 "한 판에 좌석당 정확히 2회"를 확인하며, 수정 전 같은 판은
**1,174회**를 묻는다.

**크기 정정.** 커밋 `ab48e0c`의 메시지는 이 항목을 "0.9s 중 0.62s"라고 적었는데 **과대평가**다.
0.62초는 **CPU 시간**이고 그 실행은 8 worker 병렬이라 벽시계로는 그 1/8인 약 0.08초, 즉
**+0.9s의 약 4~9%**다. `ms/decision` 열의 회귀는 사실상 100% 이 항목이지만, 총 소요 시간에서는
소수 항이다. 커밋은 다시 쓰지 않고 여기에 정정을 남긴다([lessons.md](../lessons.md)).

### (b) `88c0ef7` — base 게임에서 확장 존을 매 복사마다 훑던 검증

`GameState.__post_init__`과 `PlayerState.__post_init__`은 **모든 복사마다** 돌고, 엔진은 step당
상태를 여러 번 복사한다(측정: `dataclasses._replace` step당 6.05회). 그 안의 중복 검사 4건은
확장이 소유한 존(Contract·Skill/Commander·Tech tile·Bene Tleilax)에 대한 것인데, base 게임은
그 존이 게임 내내 비어 있는데도 매 복사마다 tuple과 set을 만들어 그것을 증명하고 있었다.

이제 모듈 플래그가 각 검사를 가른다. 모듈이 켜져 있으면 이전과 똑같이 훑고, 꺼져 있으면
합법적인 내용물이 "아무것도 없음"뿐이므로 빈지 여부만 본다 — 그 경우를 이미 지키고 있던
"모듈이 필요하다" 오류가 그대로 담당한다. 빈 컬렉션은 이 검사들을 구조적으로 전부 만족하므로
**거부되던 상태가 새로 허용되는 일은 없다**.

구조 증가 자체(GameState 필드 31 → 48, PlayerState 42 → 78)는 확장 4종을 한 frozen dataclass에
담은 대가이고, 이 커밋의 범위가 아니다.

### 두 수정의 개별 기여

세 트리를 같은 실행에서 번갈아 5회 재고 중앙값을 쓴 것이다(8 worker).

| 트리 | 중앙값 | 직전 대비 | heuristic ms/decision |
|---|---:|---:|---:|
| `2579d60` (수정 없음) | 16.50s | — | 0.082 |
| `ab48e0c` (Protocol만) | 16.30s | **−1.2%** | **0.044** |
| `88c0ef7` (둘 다) | 15.80s | **−3.1%** | 0.045 |

읽는 법이 중요하다. **(a)는 `ms/decision` 회귀의 사실상 전부(−46%)지만 총 소요 시간에서는 −1.2%**
이고, 벽시계를 실제로 줄인 쪽은 **(b)의 −3.1%**다. 계측 열 하나를 완전히 고치는 수정과 실행을
빠르게 하는 수정이 서로 다른 것이었다.

실행 간 편차는 같은 트리에서 ±0.5초(약 3%) 수준이므로(위 2절의 16.40s와 이 표의 16.50s가 같은
트리다) 개별 수치는 그 폭 안에서 읽어야 한다. 합계 −4~−5.5%는 세 번의 독립 실행에서 모두 같은
방향·같은 크기로 나왔다.

## 4. 배제한 설명

- **worker 기동·import·pool 오버헤드가 원인** — 아니다. 단일 프로세스(`--workers 1`)에서 회귀가
  **더 크게** 나온다(1.66배). 두 기준선의 rollout 절도 129.8s → 190.8s(1.47배)로 같은 비율인데,
  191초짜리 실행에서 pool 기동은 0.3% 미만이다.
- **에이전트가 느려졌다** — 아니다. `random_agent.py`는 구간 내 변경이 0줄인데 보고된 비용은
  6배가 됐다. 3(a)의 상수가 원인이다.
- **게임이 더 길어졌다** — 아니다. step 63,216 → 64,288(+1.7%)뿐이다. 비용은 step당이다.
- **기계가 바뀌었다** — 아니다. 두 리포트 모두 Apple M4로 적혀 있고, 이 저장소에서 다른 기계로
  재현했다.
- **RL 관측 인코더가 커져서**(3,166 → 4,323 int) — 아니다. 그 인코더는 `training/`과 `adapters/`
  에서만 import하며 tournament 경로는 지나가지 않는다.

## 5. 남은 비용: 콘텐츠의 대가와 아직 남은 후보

수정 뒤에도 base 기준선 대비 약 1.5배가 남는다. 정적 분석(에이전트 15개, 163 커밋 전수)과
프로파일이 함께 지목한 항목을 크기 순으로 적는다. **아래는 측정된 사실이 아니라 다음 세션의
작업 후보**이며, 규칙 동작을 바꾸는 것은 하나도 없다.

1. **상태 재구성의 폭** — 필드 31 → 48 / 42 → 78. 매 `replace()`가 그만큼의 `getattr`과
   `object.__setattr__`을 친다. 실측: step당 `getattr` 156 → 298회. 줄이려면 확장 상태를 별도
   레코드로 빼는 설계 변경이 필요하다(엔진 전반에 걸치므로 메인 세션의 판단 사항).
2. **legal action 열거** — frame 종류별 provider가 대략 두 배가 됐고(TURN 3→7, REVEAL 7→16),
   `core/engine.py:112`가 runner가 이미 만든 legal 집합을 검증하려고 **한 번 더 전부 열거한다**
   (실측: `legal_actions` 호출이 결정 수의 정확히 2배). 후자는 이 구간 이전부터 있던 안전
   가드이므로 없애는 것은 성능이 아니라 **설계 판정**이다.
   base에서 항상 `()`만 돌려줄 수 있는데 O(1) 게이트가 없는 provider 6개
   (`legal_sardaukar_commander_actions`, `legal_commander_deployments`,
   `legal_commander_withdrawals`, `legal_graft_switch_actions`, `legal_tech_reveal_actions`,
   `legal_skill_trash_actions`)는 3(b)와 같은 종류의 안전한 수정 대상이다.
3. **자동 진행 사슬** — `_advance_automatic`의 sweep이 2 → 4, 훅이 3 → 6이 됐고 일부는 게이트가
   없거나 예외 기반이다.
4. **`observe_state`** — `PublicPlayerView` 필드가 37 → 66이고 결정마다 4좌석 전부 만든다.
   `run_policy_game`은 `random` 좌석에도 관측을 만들어 건네는데 그 좌석은 쓰지 않는다.
5. **이벤트 로그의 전량 복사** — step 수에 대해 2차식이라 630 step 게임에서는 작지만, M10 자기
   대국과 깊은 rollout에서는 커진다.

## 6. 앞 세션의 용의자에 대하여

인수인계는 `6782c89`(OQ-057)가 들여온 `agent_effects.py`의 dry-run과 8칸 `_UNAVAILABLE_CACHE`를
용의자로 적었다. 실측하면 **소수 항**이다: 100판 단일 프로세스에서 호출 40,250회 중
**28,634회가 캐시 적중**(71%)이고 누적 시간은 전체의 **2.7%**다. 심는 위치도 두 곳 다
`pending_agent_effect`가 참인 AGENT_EFFECTS frame 안쪽이라 base 게임의 대부분 step은 닿지 않는다.

OQ-057의 의미(조건이 거짓인 의무 box는 turn이 끝날 때까지 기다린다)는 확정된 디자이너 판정이며,
성능을 이유로 건드릴 수 없다(`AGENTS.md`, [lessons.md](../lessons.md)).

용의자 지목이 틀렸다는 것 자체보다, **읽어서 고른 용의자를 재보지 않고 인수인계에 적은 절차**가
문제였다. [lessons.md](../lessons.md)의 2026-09-10 항목에 남겼다.
