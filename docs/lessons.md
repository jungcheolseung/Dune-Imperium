## 2026-08-28 — 규칙 문서를 확인하지 않고 리뷰 지적을 반영함

- 무슨 일: 코드 리뷰 finder가 "Intrigue로 얻은 spice가 Harvest 계약 판정을 오염시킨다"고 지적했고, 규칙 문서를 열어 보지 않은 채 Intrigue 보상 spice를 Harvest 합계에서 제외하는 보정을 구현·테스트·커밋했다(`7f24ac0`).
- 실제 규칙: [`rules/choam-module.md`](rules/choam-module.md)에 "Harvest contract는 Maker space에 Agent를 보내고, 그 turn에 **모든 출처를 합쳐** 표시된 양의 spice를 얻으면 완료한다 `[Main p. 16]`"라고 이미 적혀 있었다. 즉 Intrigue 보상 spice도 합산 대상이다. 사용자가 지적해 `08207bc`로 되돌렸다.
- 원인: 리뷰 finder의 서술을 규칙 근거로 착각했고, 기존 판정식(순증가 = 수확)을 보고 "수확만 센다"는 전제를 스스로 만들어 냈다.
- 재발 방지: 규칙 동작을 바꾸는 모든 변경(버그 수정, 리뷰 반영, 테스트 기대값 포함)은 먼저 `docs/rules/`의 해당 문장과 인용을 확인하고 커밋 메시지나 테스트 주석에 그 근거를 적는다. 문서가 침묵하면 구현하지 않고 `open-questions.md`에 올린다. `AGENTS.md`와 `CLAUDE.md`에 이 규칙을 명문화했다.

## 2026-09-06 — 백그라운드 학습 실행의 조용한 죽음을 1시간 40분 동안 놓침

- 무슨 일: 150 iteration self-play 학습을 백그라운드로 돌리고 완료 알림만 기다렸다. 학습 프로세스는 41 iteration에서 메모리 부족으로 죽었지만(정책이 되돌리기 행동을 반복하도록 학습돼 게임당 결정 수가 680→1,793으로 늘고, learner가 11만 행 × 4,354 logit을 한 번에 forward), 셸 래퍼와 고아 worker 8개가 살아 있어 작업이 "실행 중"으로 보였고 사용자가 물어볼 때까지 알아채지 못했다.
- 원인: 완료 알림은 프로세스 트리 전체가 끝나야 오는데, 자식이 남으면 오지 않는다. 진행 로그(`training.jsonl`)를 보지 않았다.
- 재발 방지: 긴 실행은 `nohup ... > log &`로 띄우고 진행 로그를 주기적으로 확인하는 Monitor(진행·오류·프로세스 종료를 모두 이벤트로)를 같이 건다. 실행 전에 배치 크기 상한(게임당 결정 상한, step penalty)과 메모리 상한(전체 배치 forward 금지)을 확인한다. `TrainConfig.max_steps` 기본값을 4,000으로 낮추고 learner의 값 계산을 minibatch로 나눈 것이 이 사건의 수정(`3a028fe`)이다.

## 2026-09-09 — 백그라운드 대기 루프가 자기 자신을 감지해 끝나지 않음

- 무슨 일: 소크·A/B·pytest를 백그라운드로 돌리고 결과를 기다리려고 `until [ "$(pgrep -fc dune-imperium-sweep)" -eq 0 ]; do sleep 20; done` 형태의 대기 루프를 6개 띄웠다. 대상 작업은 전부 정상 종료(`exit=0`)했는데 대기 루프는 하나도 끝나지 않았고, 사용자가 "지금 실행 중인 작업 뭐야? 다 끝난 거 아니었나"라고 물어서야 알아챘다.
- 원인: `pgrep -f`는 패턴을 모든 프로세스의 **전체 명령줄**과 대조하는데, 그 루프를 실행하는 zsh 래퍼의 명령줄에 패턴 문자열(`dune-imperium-sweep`, `ab_tournament.py`, `pytest`)이 그대로 들어 있다. 그래서 대상이 모두 죽어도 카운트가 최소 1이라 조건이 영원히 거짓이었다. `pgrep`은 자기 자신은 제외하지만 루프를 감싼 셸은 제외하지 않는다.
- 피해: CPU 부하는 없었지만(전부 `sleep`) 백그라운드 작업 슬롯 6개를 계속 점유했고, 더 나쁘게는 같은 `pgrep`으로 진행 상황을 폴링했기 때문에 **이미 끝난 작업을 "아직 실행 중"이라고 사용자에게 잘못 보고했다**. 프로세스 수를 완료 판정의 근거로 쓴 것이 오보의 직접 원인이다.
- 재발 방지: 프로세스의 존재 여부로 완료를 판정하지 않는다.
  1. 하네스가 추적하는 백그라운드 작업(`run_in_background`)은 완료 알림이 오므로 별도의 대기 루프를 만들지 않는다.
  2. 직접 띄운 `nohup` 작업은 종료 코드를 로그에 남기고(`nohup sh -c '... > log 2>&1; echo "exit=$?" >> log' &`) 그 표식을 기준으로 판정한다. 이 세션의 base 소크가 이 방식이었고 유일하게 오판이 없었다.
  3. 굳이 `pgrep`을 써야 하면 자기 명령줄과 일치하지 않게 패턴을 쓴다(`pgrep -fc '[d]une-imperium-sweep'`). 실측(2026-09-09): 대상이 살아 있을 때 브래킷 형태는 1(대상만), 평문은 2(대상 + 폴러의 셸)를 세고, 대상이 끝나면 평문은 1에서 멈춘다 — 이것이 위 루프가 끝나지 않은 정확한 이유다. **단서**: 같은 명령줄에 평문 형태가 한 번이라도 더 나오면(예: 두 형태를 나란히 비교하는 진단 명령) 셸의 명령줄이 다시 매칭되어 브래킷 트릭도 무력해진다. 그래서 1·2번이 우선이고 3번은 최후 수단이다.
- 2026-09-06의 "백그라운드 학습 실행의 조용한 죽음" 항목과 짝이다: 그때는 살아 있는 고아 프로세스를 실행 중으로 오인했고, 이번에는 죽은 작업을 실행 중으로 오인했다. 두 경우 모두 **프로세스가 아니라 작업이 남긴 산출물(진행 로그, 종료 코드)**을 봤어야 했다.

## 2026-09-10 — 재보지 않은 용의자를 인수인계에 귀인으로 적음

- 무슨 일: 앞 세션이 처리량 35% 회귀(59.25 → 38.71 games/s)의 원인을 커밋 diff만 읽고
  `6782c89`(OQ-057 dry-run + 8칸 `_UNAVAILABLE_CACHE`)로 지목해 인수인계에 "용의자"로 적었고, 그
  문장이 다음 세션의 출발점이 됐다. 실측하니 그 항목은 누적 시간의 **2.7%**였다(호출 40,250회
  중 28,634회 캐시 적중). 실제 원인은 전혀 다른 두 가지였다 — 계측 구간 **안**에서 결정마다 돌던
  `runtime_checkable` Protocol의 `isinstance`(`ab48e0c`)와, base 게임에서도 매 상태 복사마다 도는
  확장 존 검증(`88c0ef7`) — 이고, 회귀 자체는 "step당 엔진 CPU 1.6배"라는 넓은 현상이었다.
- 원인: diff에서 "새로 생긴 비싼 것"을 찾으면 그럴듯한 후보는 반드시 나오는데, 그것이 실제로
  **몇 번 도는지**를 재지 않았다. 163 커밋 구간에서 가장 눈에 띄는 변경이 가장 비싼 변경일
  이유가 없다.
- 재발 방지: 성능 귀인은 지목이 아니라 측정으로 적는다. (1) 회귀가 재현되는지와 (2) 후보가
  step당 몇 번 도는지를 재기 전에는 인수인계에 "용의자"로만 적고 원인으로 적지 않는다. 측정은
  CPU 경합에 면역인 지표(cProfile의 **호출 횟수**, step 수)를 먼저 쓰고, 소요 시간은 기계가
  조용할 때 트리를 번갈아 잰다. cProfile의 **누적 시간**은 호출 수에 비례해 부풀므로 트리 간
  비교에 쓰지 않는다 — 이 세션에서 실제로 한 번 정반대 결론을 냈다. 절차와 수치는
  [evaluation/throughput-2026-09-10.md](evaluation/throughput-2026-09-10.md)에 있다.

## 2026-09-10 — 병렬 실행에서 CPU 시간을 벽시계 기여로 적음

- 무슨 일: Protocol `isinstance` 수정(`ab48e0c`)의 커밋 메시지에 그 항목이 "+0.9초 중 약 0.62초"
  라고 적었다. 0.62초는 62,228 결정 × 2회 × 5us = **CPU 시간**인데 그 실행은 `--workers 8`
  병렬이라 벽시계로는 약 1/8인 0.08초, 즉 **4~9%**다. 끝에서 끝까지 실측한 값도 두 수정을 합쳐
  −5.5%였다.
- 원인: 리포트의 `ms/decision` 증가분(+0.005 ms)이 예측과 정확히 맞아떨어지는 데 만족해 그 값을
  벽시계 기여로 바로 옮겼다. 그 열은 좌석 하나의 CPU 시간이고 총 소요 시간은 worker 8개로
  나뉜다.
- 재발 방지: 성능 기여를 적을 때 단위를 명시한다(core-seconds / wall-seconds). 병렬 실행에서는
  CPU 절감을 worker 수로 나눈 뒤 비율을 적고, 커밋 메시지에는 **끝에서 끝까지 실측한 벽시계
  A/B**로 확인한 값만 적는다. 커밋은 다시 쓰지 않고 정정을
  [evaluation/throughput-2026-09-10.md](evaluation/throughput-2026-09-10.md) 3(a)에 남겼다.

## 2026-09-10 — 자기 자신을 매칭하는 대기 루프를 한 세션에 세 번 만듦

- 무슨 일: 소크와 벤치마크가 끝나기를 기다리려고
  `until ... && ! pgrep -f "dune-imperium-sweep|pytest"; do sleep 15; done`을 백그라운드로 띄웠다.
  `pgrep -f`는 **전체 명령줄**을 매칭하는데 그 패턴이 루프 자신의 명령줄에도 들어 있어 조건이
  영원히 참이 됐다. 기다리던 작업은 진작 끝나 알림까지 왔는데도 루프는 timeout까지 돌았다.
  같은 실수를 한 세션에 **세 번**(`b5yu128i8`, `bqqaccl7e`, `bvqfqs4eq`) 했고, 그중 둘은 세션
  마무리 보고 시점까지 "실행 중"으로 남아 있었다.
- 원인: (1) 첫 번째에서 원인을 파악하고도 기록하지 않아 같은 패턴을 두 번 더 썼다. (2) 애초에
  기다릴 필요가 없었다 — 백그라운드 작업은 완료 알림을 스스로 보낸다. (3) "실행 중인 작업"을
  프로세스 목록(`ps`/`pgrep`)으로만 확인하고 도구가 추적하는 작업 목록을 보지 않아, 남아 있는
  둘을 못 보고 "정리 완료"라고 보고했다.
- 재발 방지: 긴 작업은 **기다리지 않는다**. 완료 알림을 받고 그동안 다른 일을 한다. 꼭 블로킹해야
  하면 도구의 작업 조회 기능으로 블로킹하고, 셸로 기다려야 하면 프로세스 존재가 아니라
  **파일·센티널**을 기다린다(`until grep -q DONE out.log; do sleep 5; done`). 프로세스를 봐야만
  하면 자기 자신이 걸리지 않게 한다(`pgrep -x`, 또는 `pgrep -f pat | grep -vw $$`). 쓸모없어진
  작업은 **그 즉시 중지**하고, 세션을 마치기 전에 남은 작업을 훑는다. 상태 보고는 프로세스 목록이
  아니라 도구의 작업 목록을 근거로 한다.

  아이콘 하나뿐이라 Dagger 배치가 2배가 되고 Assembly Hall·Gather Support가 그것을
  흡수해 **Combat 배치 비중이 50.2% → 46.5%**로 떨어졌다.
- 축소도 답이 아니었다: 보드 표의 최소 간격(0.05) 안으로 항을 줄이자 base+CHOAM은
  회복됐지만(−0.2%p, +0.2%p) **전 확장은 결정 수까지 똑같은 −8.6%p**를 재현했다.
  확장 룰셋은 두 칸짜리 표를 쓰므로 21칸이 동점이고, 그 위에서는 **어떤 배율의 카드
  항이든 공간을 고르는 항**이 된다. 배율로 고칠 수 있는 문제가 아니었다.
- 원인: `score_action`은 한 행동만 보고 **모든 계열과 모든 공간을 가로질러** 순위를
  매긴다. 그래서 "같은 공간에 도달하는 카드들 사이의 동점"이라는 국소적 판단을 점수에
  더하면 국소적으로 남지 않는다. 항의 크기를 옳게 잡는 문제로 오해했지만, 실제로는
  **적용 범위**의 문제였다.
- 재발 방지: 한 인자 계열 안의 동점을 깨는 판단은 점수에 더하지 않고, 동점 집합이
  결정된 **뒤에** 그 집합 안에서 적용한다. 이 항목은 `choose_action`이 seeded 추첨으로
  공간을 먼저 확정한 다음, 그 공간에 도달하는 배치들 사이에서만 카드를 고르도록 다시
  구현했다(`cheapest_card_for_the_same_space`). 새 항이 공간 순위를 건드릴 수 있는지는
  구현 전에 "이 항이 0이 아닌 차이를 만드는 두 행동이 같은 공간인가"로 자문한다.
- 2026-09-10 저녁의 "확장 공간 overlay −34%p" 항목과 같은 뿌리다. 그때는 보너스를
  더해서, 이번에는 비용을 빼서 같은 Combat/비Combat 균형을 무너뜨렸다. 보드 표는
  효용 척도가 아니라 **그 균형에 맞춰 조정된 표**이므로, 그 위에 같은 크기의 항을
  더하거나 빼는 변경은 균형 재설계로 취급한다.

## 2026-09-11 — "실행 중인 작업 없음"을 작업 목록 없이 세 번째로 잘못 보고함

- 무슨 일: 세션 마무리 보고에 "백그라운드 작업은 남아 있지 않다"고 적었는데, 사용자가 "지금
  실행 중인 작업 1개 뭐야"라고 물어 확인하니 실패한 스윕 5 첫 실행의 로그를 감시하던 Monitor
  (`b91mxvedk`)가 살아 있었다. 2026-09-09와 2026-09-10에 같은 성격의 오보를 두 번 기록하고도
  세 번째다.
- 원인 두 가지.
  1. 보고 근거가 또 **산출물**이었다 — 스크래치 로그의 `exit=` 표식과 `restored` 표식을 훑고
     "다 끝났다"고 적었다. 이전 교훈("도구의 작업 목록을 근거로")은 원칙만 있었고, **어느 ID를
     어떻게 조회하는지**가 절차로 없었다. 하네스에는 작업 목록 도구가 없어서 내가 띄운 ID를
     기록하지 않으면 조회할 대상 자체가 없다. 그래서 "확인해야지"라는 의도가 실행으로 이어질
     고리가 없었다.
  2. Monitor 명령의 구조 자체가 매달린다 — `tail -f log | grep | while read; do ... exit; done`은
     종료 표식을 읽고 `while`이 끝나도 `tail -f`가 다음 write에서야 SIGPIPE를 받으므로, 조용해진
     로그 위에서는 영원히 산다. 같은 모양의 Monitor를 이 세션에 여섯 개 썼고 그중 하나가 남았다.
- 재발 방지(`CLAUDE.md` "Background-task ledger" 절에 절차로 명문화):
  1. 작업을 띄우면 **즉시** `<scratchpad>/tasks.md`에 ID와 용도를 한 줄 적는다.
  2. 실행 상태를 입에 올리기 전에는 그 파일의 **모든 ID**에 `TaskOutput(block=false)`를 돌리고
     그 결과로만 말한다. 로그·표식·`ps`는 근거가 아니다.
  3. 단일 완료 알림에는 Monitor를 쓰지 않는다. `run_in_background` Bash + 파일 표식 대기
     (`until grep -q 'exit=' log; do sleep 10; done`)를 쓴다.
  4. 쓸모없어진 ID는 `TaskStop`하고 파일에 완료 표시를 한다. 표시 안 된 ID가 있으면 마무리가 아니다.
- 교훈의 교훈: 같은 실수를 두 번 기록했는데도 재발한 이유는 기록이 "무엇을 하지 말라"였지
  "그 순간 무엇을 하라"가 아니었기 때문이다. 재발 방지는 **손이 가는 절차**로 적는다.

## 2026-09-16 — 고정 표가 현행 표의 나머지 항목을 물려받는 함정(발견, 사고 전에 잡음)

## 2026-09-16 — A/B가 도는 동안 작업 트리를 고쳐 대조군을 바꿈

- 무슨 일: heuristic 표 밖 항의 A/B(스크래치 변형 vs `heuristic`, `--workers 8`)가 도는 사이에
  같은 변형을 저장소의 `HeuristicAgent`로 옮겨 적었다(채택 준비). 대회 worker는 `spawn`으로 뜨며
  **셀이 시작할 때의 작업 트리**를 import하므로, 그 뒤에 시작한 셀의 `heuristic`(대조군)은 이미
  변형과 같은 코드였다 — 2라운드 전체가 변형 vs 변형(25.0% 미러)을 재고 있었고, 첫 시도의 rollout
  control 셀은 반쯤 써진 모듈을 import한 worker가 죽어 `BrokenProcessPool`로 끝났다. 발견은 2라운드
  첫 셀 결과가 아니라 "저장소 port가 스크래치 combo와 결정까지 같다"는 확인 뒤에 대조군 이름을

- 원인: 스크래치 변형은 `sitecustomize`로 registry에 얹히지만 대조군 `heuristic`은 작업 트리의
  코드다. 측정 중에 그 코드를 바꾸면 안 된다는 것을 알면서도, "저장소 반영은 커밋하지 않으면 영향이

  (3) 셀 스크립트는 첫 줄에 `git rev-parse HEAD`와 `git status --short`를 함께 적어, 결과 파일이

## 2026-09-21 — 충돌 "시험"으로 돌린 `git replay`가 master ref를 옮김

- 무슨 일: origin/master로 rebase해도 되는지 보려고, 작업 트리를 건드리지 않는 시험 삼아
  `git replay --onto origin/master origin/master..master`를 두 번 돌렸다(첫 번째는 출력을 버렸다).
  git 2.54의 `git replay`는 기본값이 `--ref-action=update`라 **ref를 직접 갱신**한다. master가 replay된
  커밋으로 옮겨졌고 인덱스·작업 트리는 rebase 전 master에 남았다. 그런데 사용자에게는 "작업 트리를 건드리지
  않는 시험"이라고 보고했다. 실제 rebase를 시작하자 git이 "인덱스에 커밋하지 않은 변경"으로 거부했고,
  `git status`가 원격 22커밋의 변경을 거꾸로 staged로 보여 줘서 알았다.
- 피해: 없음. 인덱스 tree가 rebase 전 master의 tree와 같음을 `git write-tree`로 확인하고, master를 그 커밋으로
  `git reset --soft`한 뒤 정식으로 `git rebase`했다. 같은 checkout에서 돌던 학습은 작업 트리가 바뀌지 않아
  영향이 없었다.
- 원인: `git replay`가 update-ref 명령을 출력만 하던 예전 동작을 기억으로 믿고 `git replay -h`를 보지 않았다.
  EXPERIMENTAL로 표시된 명령이라 버전마다 기본값이 바뀐다.
- 재발 방지:
  1. ref를 바꾸지 않는 충돌 시험은 `git merge-tree --write-tree <ours> <theirs>`로 한다. 커밋 하나하나의 충돌을
     봐야 하면 `git replay --ref-action=print`처럼 출력만 하라고 명시한다.
  2. "아무것도 바꾸지 않았다"고 보고하기 전에 `git reflog -2 <branch>`로 ref가 그대로인지 확인한다.
