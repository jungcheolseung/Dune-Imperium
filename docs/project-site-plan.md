# 프로젝트 웹사이트 계획

작성일: 2026-10-20. **Hugo 화면·검색·배포 workflow 구현, 로컬 검증 완료; 공개 전.** 사용자 요청: 프로젝트 소개, 규칙 엔진 구현기, AI 학습 실험,
업데이트 소식, 다운로드, 사용법을 담는 GitHub 저장소의 사이트와 추가로 필요한 내용을 계획한다.

## 1. 목표와 기본 방향

처음 방문한 사람이 프로젝트를 이해하고, 자기 상황에 맞는 방법으로 게임을 시작하며, 개발 과정을 계속 읽을 수 있는
사이트를 만든다. 한국어를 먼저 제공한다. 프로젝트 이름은 README의 **Dune: Imperium AI**를 우선 사용한다.
전체는 프로젝트 웹사이트이며, 개발 블로그는 그 안의 한 구역이다. 사용자 결정(2026-10-20)으로 사이트 소스 폴더는
`website/`로 정한다. 기존 `docs/`는 개발 문서로 유지한다.

방문자는 세 가지 경로로 들어온다.

| 방문 목적 | 첫 안내 | 도착할 곳 |
| --- | --- | --- |
| AI와 혼자 두거나 친구들과 방을 만들기 | 설치하고 시작하기 | 다운로드 → 설치 → 첫 게임 만들기 |
| 친구가 만든 방에 참여하기 | 친구 방에 참여하기 | 참가자 가이드; 호스트가 보낸 방 링크 사용 |
| 엔진·AI 개발 과정 알아보기 | 개발 이야기 읽기 | 규칙 엔진 구현기·AI 학습 실험 |

홈에서 설치가 필요한 사람과 방에 참여만 하는 사람을 구분한다. 사이트의 버튼은 실제로 이어지는 설치·접속 안내로
연결한다. 사이트 자체가 게임 서버를 제공하는 것으로 보이게 하는 "지금 바로 플레이" 버튼은 두지 않는다.

## 2. 조사로 확인한 출발점

- GitHub 저장소 `jungcheolseung/Dune-Imperium`은 공개 상태이며 Pages는 꺼져 있다(2026-10-20 API 확인).
- 같은 날 GitHub Releases 조회 결과는 0건이다. `pyproject.toml`의 패키지 버전을 공개 배포판이 있는 근거로 쓰지 않는다.
- 기존 구조는 Python 게임 엔진·플레이 서버와 Markdown 문서다. 사이트용 프레임워크·배포 workflow는 없다.
- [런처 스크립트](../scripts/launcher/)는 **프로젝트 폴더와 uv가 준비된 상태**에서 의존성을 설치하고 바로가기를 만든다.
  스크립트 파일 하나만 받아 실행하는 독립 설치 프로그램은 아니다.
- [호스트 가이드](remote-play-host-guide.md)와 [런처 계획](server-launcher-plan.md)에 macOS 검증과 Windows 실기 검증 미완료가
  구분돼 있다. OS용 스크립트가 있다는 사실과 해당 OS에서 검증됐다는 사실을 나눠 표시한다.
- 학습 망은 git 밖의 `checkpoints/`, 카드·보드 등의 원본은 비공개 에셋 저장소에 있다. 소스 내려받기에 포함되지 않는다.
- 계획 기준은 원격 master `e7e9ad4f`다. 메인 체크아웃은 보존하고 별도 worktree에서 계획을 작성했다.

## 3. 메뉴와 콘텐츠

상단 메뉴는 **소개 / 다운로드 / 사용법 / 개발 이야기 / 업데이트 / 도움말**로 한다. 로고는 홈으로,
GitHub 링크는 별도로 둔다. 규칙 엔진과 AI 실험은 개발 이야기 아래에서 골라 볼 수 있게 한다.

| 구역 | 내용 | 첫 공개 범위 |
| --- | --- | --- |
| 홈 | 프로젝트 한 줄 소개, 시작 경로 두 개, 주요 기능, 최신 글·업데이트 | 필수 |
| 소개 | 만든 이유, 누구를 위한 것인지, 플레이 방식, 지원 기능·확장, 현재 한계 | 필수 |
| 다운로드 | 실제 받을 수 있는 항목, 설치 요구 사항, OS 검증 상태, 배포판별 안내 | 필수 |
| 사용법 | 혼자 시작하기, 호스트로 방 만들기, 친구 방 참여, 기본 조작·저장·복구 | 필수 |
| 개발 이야기 → 규칙 엔진 | 규칙을 코드로 옮기는 과정, 합법 행동·숨은 정보·결정론·효과 조각·검증 | 첫 글 1편 |
| 개발 이야기 → AI 실험 | AI 종류, self-play, 정책·가치 망과 탐색, 실험 결과와 실패에서 배운 점 | 첫 글 1편 |
| 업데이트 | 사용자가 체감하는 변경, 배포일·버전, 업데이트 방법, 저장·모델 호환 안내 | 첫 소식 1편 |
| 도움말 | FAQ, 설치·접속·이미지·AI 문제 해결, 버그 제보 | 필수 |

추가 콘텐츠는 다음 순서로 넣는다.

1. **지원 현황:** 기본 게임·확장·모듈·플레이 방식과 구현/검증/미지원 상태. 소개 안에 먼저 넣는다. Rise of Ix의 Epic Game Mode
   지원을 Rise of Ix 전체 지원으로 오해하지 않도록 실제 구현 단위로 쓴다. 웹사이트의 모바일 대응과 게임의 모바일 검증 상태도 구분한다.
2. **AI 선택 안내:** 기본 AI와 추가 망이 필요한 탐색 AI의 차이, 난이도, 준비물, 대기 시간. 사용법 안에 넣는다.
3. **로드맵:** 완료·진행 중·검토 중을 짧게 보여 준다. 개발 인수인계의 작업 목록을 독자에게 필요한 수준으로 정리한다.
   약속하지 않은 기능의 출시일을 붙이지 않는다. 소개 하단에 먼저 넣는다.
4. **화면 둘러보기:** 기본 조작과 한 턴의 흐름을 설명하는 그림 또는 짧은 시연. 공개 범위를 확인한 자료로 준비한다.
5. **플레이 사례·리플레이 분석:** AI가 고른 수를 한 장면씩 설명하는 연재. 공개 가능한 사례가 생기면 개발 이야기 안에 추가한다.
6. **참여 안내:** 버그·기능 제안·문서 수정 방법을 도움말에 둔다. 별도 커뮤니티 운영은 이용자가 늘면 검토한다.

본문이 없는 메뉴나 예고 글만 있는 카테고리를 만들지 않는다. 초기에는 소개·사용법·도움말의 하위 절로 시작하고,
내용이 길어지면 URL을 유지하거나 리디렉션하면서 독립 페이지로 나눈다.

## 4. 홈과 읽기 경험

홈은 다음 순서로 구성한다.

1. 프로젝트 이름, 무엇을 할 수 있는지 설명하는 짧은 문장, **설치하고 시작하기 / 친구 방에 참여하기** 버튼.
2. AI 대전·친구와 멀티플레이·선택 모듈 등 핵심 기능 세 가지와 소개 링크.
3. 화면을 이해할 수 있는 시연 한 개. 공개용 이미지가 준비되지 않으면 직접 만든 구조도로 시작한다.
4. 최신 업데이트 한 건과 개발 이야기 최대 세 편.
5. 지원 현황 요약, 도움말과 GitHub 링크.

사막 계열의 절제된 색과 읽기 편한 본문을 기본안으로 삼는다. 코드·표·실험 그래프를 읽기 좋게 하고, 글에는 목차와
관련 글을 둔다. 휴대폰에서는 메뉴·표·코드 블록이 화면을 가리지 않게 한다. 그림과 배경 연출보다 정보와 조작이 먼저다.

## 5. 다운로드와 배포판

### 첫 공개: 현재 가능한 설치를 정확히 안내

- 릴리스가 없다면 "현재는 소스 기반 설치를 제공합니다"라고 안내하고 저장소·설치 가이드로 연결한다.
- macOS와 Windows의 절차 및 검증 상태를 각각 표시한다. Linux는 CLI 설치 경로와 실제 확인 범위만 적는다.
- 런처 스크립트만 별도 다운로드시키지 않는다. 프로젝트 폴더 준비 → uv 준비 → 런처 설치 순서를 연결한다.
- 참가자에게는 별도 게임 설치가 필요 없다는 안내를 다운로드 페이지에서도 찾을 수 있게 한다.
- 탐색 AI는 별도 준비 항목으로 설명한다. 공개 망 파일이 준비되기 전에는 다운로드 버튼을 만들지 않는다.
- 변경될 수 있는 개발판은 "개발판"으로 표시한다. 정식 릴리스와 혼동하지 않게 한다.

### 후속 배포 작업: GitHub Releases와 연결

웹사이트와 별개의 작업으로 첫 배포판을 준비한다. 특정 태그의 소스와 실제 검증한 설치 절차를 묶고, 깨끗한 환경에서
설치 → 실행 → 첫 판 → 저장·재실행을 확인한 OS부터 배포 대상으로 삼는다. 소스 ZIP 설치는 Git clone 설치와 별도로
확인한다. 독립 실행 `.app`·`.exe`·설치 패키지는 패키징·실기 검증을 거치는 별도 작업이다.

다운로드 정보는 한 곳(`website/data/downloads.yaml` 예정)에서 관리한다. 실제 릴리스 태그, 파일 URL·크기·검증값,
OS·아키텍처와 검증 상태, 설치 가이드, 저장·AI 모델 호환 정보를 기록한다. 홈과 다운로드 페이지는 같은 정보를 읽는다.
파일은 GitHub Releases에서 제공하고 사이트 저장소에는 복제하지 않는다. 공개된 파일과 안내가 준비된 항목만 표시한다.

학습 망을 공개할 때는 대응하는 프로그램 버전·action codec·관측·망 형식을 함께 기록하고 로드·플레이를 확인한다.
프로그램만 받는 경로와 선택 모델을 추가하는 경로를 분리한다. 카드·보드 원본은 기존 비공개 에셋 정책을 유지한다.

## 6. 사용법과 기존 문서의 관계

사용법의 첫 화면에서 **혼자 플레이 / 방 만들기 / 친구 방 참여**를 고른다.

| 안내 | 최소로 답할 질문 | 기존 근거 |
| --- | --- | --- |
| 처음 한 판 | 무엇을 설치하고 어떻게 실행하며 게임을 만드는가 | [README](../README.md), [호스트 가이드](remote-play-host-guide.md) |
| 친구와 플레이 | 누가 서버를 켜며 참가자는 무엇을 준비하는가 | [멀티플레이 입구](remote-play-guide.md), [참가자 가이드](remote-play-player-guide.md) |
| 기본 조작 | 카드·칸 선택, 확정·턴 종료, 되돌리기, 저장·이어 하기 | 현재 UI 도움말과 서버 동작 |
| AI 선택 | 별도 파일이 필요한가, 어떤 좌석을 고르면 되는가 | README, [탐색 AI 설명](search-ai.md) |
| 그림과 화면 | 이미지가 없어도 시작할 수 있는가, 이미지는 어떻게 연결하는가 | [로컬 이미지](local-images.md) |
| 문제 해결 | 실행 실패·접속 끊김·빈 좌석 없음·AI 안 보임에 무엇을 하는가 | 호스트·참가자 가이드 |

기존 문서는 개발·상세 운영의 근거로 유지하고, 사이트에는 처음 시작하는 사람이 따라 할 짧은 안내를 작성한다.
가이드마다 근거 문서와 확인한 코드 버전을 기록하고, 설치 명령·요구 사항이 바뀌면 해당 사이트 안내도 같은 작업에서 확인한다.
현재 버전을 안내하는 사용법과 과거 실험·업데이트 글을 구분한다. 과거 글은 당시 조건을 남기고 현재 시작 안내로 연결한다.

`docs/worklog/`·인수인계·규칙 문서를 통째로 자동 발행하지 않는다. 공개할 내용을 고르고, 코드 경로·비공개 자료에 기대는
설명은 독자에게 이해되는 문장으로 다시 쓴다. 공식 규칙과 프로젝트 판정은 구분하고, 규칙 글에는 관련 공식 출처를 연결한다.

이후 연재 후보는 효과 조각 엔진 전환, self-play와 평가, 망 구조 실험, 강해지지 않은 실험,
사람이 둔 판에서 발견한 문제 등이다. 개발 로그를 그대로 옮기기보다 **문제 → 시도 → 검증 → 결과·한계** 순서로 쓴다.

실험 수치에는 날짜, 코드·모델 버전, 룰셋·대전 상대, 판 수·좌석 구성, 불확실성, 근거 기록을 붙인다.
서로 다른 엔진에서 나온 승률을 현재 성능처럼 합치지 않는다. 홈에는 확인된 현재 배포판의 설명만 쓰고,
과거 실험의 높은 승률을 조건 없이 홍보 수치로 쓰지 않는다.

업데이트는 커밋 목록보다 사용자 행동을 기준으로 쓴다: 달라진 기능, 고친 문제, 사용자가 해야 할 일, 호환 주의,
관련 릴리스·사용법. 배포하지 않은 변경은 개발 소식으로 표시한다. 릴리스 본문이 배포 정보의 기준이며,
사이트의 업데이트 글은 그 내용을 설명하고 해당 릴리스로 연결한다.

## 8. 구현·운영 제안

**Hugo + GitHub Actions + GitHub Pages**를 기본안으로 한다. 사이트 소스는 `website/`에 두고 게임의 Python 의존성과 분리한다.
사이트 빌드에 `assets` 심볼릭 링크나 로컬 체크포인트가 없어도 된다. 생성된 HTML은 커밋하지 않는다.

```text
website/
  README.md           # 원고 색인·편집 지침; 공개 콘텐츠 밖
  hugo.toml
  content/
    _index.md
    about/
    downloads/
    guides/
    posts/             # category: engine / ai
    updates/
    help/
  data/downloads.yaml  # 공개 배포 항목이 생기면 사용
  layouts/
  static/
.github/workflows/website.yml
```

- 프로젝트 사이트의 `/Dune-Imperium/` 경로를 반영한다. 로컬 루트에서만 열리는 링크를 만들지 않는다.
- 사이트 폴더·workflow가 바뀐 PR에서는 빌드·링크를 확인하고, master 반영 뒤에는 사이트 변경이 있을 때 배포한다.
  사용법에 영향을 주는 문서가 바뀐 경우에도 검증을 돌리도록 경로를 잡는다. 수동 배포도 가능하게 한다.
- Pages에는 빌드 결과만 올린다. 저장소 루트나 `docs/` 전체를 배포 artifact로 삼지 않는다.
- 기본 기능은 카테고리·태그, RSS, sitemap, 글·안내의 수정일, 404 페이지, 페이지별 제목·설명이다.
- 글 메타데이터는 제목·날짜·요약·분류·태그·초안 여부를 공통으로 하고, 안내에는 확인 버전과 근거 문서,
  실험에는 근거 기록을 추가한다. 기존 글의 URL은 가능한 한 유지한다.
- 검색은 사용법·도움말을 찾을 수 있는 간단한 정적 검색으로 먼저 제공한다. 댓글·별도 계정·커스텀 도메인·전면 영문판은 후속 후보다.
- 공개용 시각 자료는 범위·이용 조건을 확인한 것만 사용한다. 처음에는 직접 만든 도표·구조도로 충분하다.

## 9. 작업 순서와 완료 조건

| 단계 | 작업 | 완료 조건 |
| --- | --- | --- |
| 1. 원고·자료 | 메뉴·URL, 소개·시작 안내·FAQ, 개발 글 2편·첫 소식, 공개용 자료 | 핵심 방문 경로마다 읽을 본문이 있고 현재 동작·검증 범위와 맞음 |
| 2. 사이트 | Hugo 레이아웃, 홈·각 구역·글 목록, 검색·RSS·sitemap | PC·휴대폰에서 읽을 수 있고 키보드 이동·표·코드·404가 정상 |
| 3. 공개 준비 | Actions, 프로젝트 경로 검증, 공개 파일 범위·링크 확인, Pages 설정 | PR 빌드와 배포 결과에서 경로·이미지·링크가 정상이며 시작 안내를 따라갈 수 있음 |
| 4. 배포판 | 검증된 설치 묶음, GitHub Release, 다운로드 정보 연결 | 새 환경에서 설치·첫 판·저장·재실행 확인, 안내와 실제 파일 일치 |
| 5. 확장 | 연재, 시연, 플레이 사례, 지원 현황·로드맵 보강 | 내용이 생긴 항목부터 추가; 사용법·다운로드의 최신성 유지 |

첫 공개는 1~3단계로 한다. **릴리스가 없어도 설치 안내를 갖춘 사이트는 공개할 수 있다.**
4단계의 배포판 작업을 사이트 디자인·글 작성과 한 묶음으로 늘리지 않는다. 각 단계는 문서·사이트·배포판 단위로 검증하고 커밋한다.

첫 공개 전에는 최소한 다음을 확인한다.

- 깨끗한 체크아웃에서 비공개 에셋·모델 없이 사이트가 빌드되고, 초안은 결과물에 나오지 않는다.
- `/Dune-Imperium/` 아래에서 메뉴·본문·CSS·검색·RSS가 동작하며 내부 링크·파일 경로가 유효하다.
- 현재 제공하지 않는 다운로드 버튼이 없고, 요구 사항·OS 검증 상태·선택 모델 안내가 실제와 맞는다.
- 사이트의 화면 대응을 게임의 모바일 지원으로 오인하게 하지 않는다.
- 홈의 시작 버튼 두 개에서 각각 설치·참가 안내에 도달한다. 안내는 해당 배포 형태의 새 환경에서 확인한다.
- 사이트가 만든 artifact에 비공개 에셋·로컬 설정·저장 파일·체크포인트가 섞이지 않는다.

원고 18개에 검색 페이지를 더했다. 홈·문서·글 목록·분류·목차·관련 글, 모바일 메뉴, 정적 검색, RSS·sitemap·404를
자체 Hugo 레이아웃으로 구현했다. 사이트 내부 링크는 `relref`로 프로젝트 하위 경로를 유지한다.
직접 만든 좌석 구성도와 표식 SVG 외의 이미지 원본은 넣지 않았다.

Hugo 0.168.0으로 경고 없이 빌드하고 HTML 34개·내부 참조 1,296개를 검사했다. Chromium에서 PC 및 320/390px 화면,
검색·한글 조합 입력·글 분류·메뉴·404·JS 없는 탐색을 확인했다. 환경 준비와 재실행 방법은
[`website/README.md`](../website/README.md)에 있다.

`.github/workflows/website.yml`은 PR에서 빌드·브라우저 검증만 하고 `master` 반영 시 Pages 배포를 실행한다.
workflow의 YAML·배포 조건과 공식 Action 버전은 확인했지만 실제 GitHub Actions 실행은 아직 하지 않았다.
**남은 것:** 공개 전 원고·게임 설치 확인, Pages의 Source를 GitHub Actions로 설정하고 검토한 변경을 master에 반영,
실제 배포·공개 주소 확인. 릴리스와 선택 모델 배포는 별개다. 현재 로컬 결과를 사이트 공개 완료로 표시하지 않는다.
