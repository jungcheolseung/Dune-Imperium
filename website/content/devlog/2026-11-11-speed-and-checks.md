## 작업 배경

플레이 서버 PC(셀러론 미니 PC)에서는 탐색 AI의 차례가 길고, Agent 턴에 세계를 16개로 늘린 뒤로 더 길어졌습니다. 시간을 아끼면 같은
탐색을 더 빨리 하거나, 같은 시간에 더 멀리 볼 수 있습니다. 한편 엔진 관문과 병합마다 도는 전체 pytest와 브라우저 E2E가 길고,
부하가 있으면 E2E 몇 개가 시간 초과로 깨져 매번 다시 돌려야 했습니다.

## 플레이아웃을 묶어 읽기 (병합 `2067caab`, 11월 10일)

탐색은 결정마다 (세계 × 후보) 수십 개의 플레이아웃을 두고, 플레이아웃의 걸음마다 모델을 한 번씩 읽었습니다. 이제 한 단계의 플레이아웃을
나란히 한 걸음씩 두며, 걸음마다 모델을 한 번에 묶어 읽습니다(같은 관측은 한 번만).

- **수가 바뀌는가.** 묶어 읽기를 끄면 master와 모든 수와 탐색 결과가 비트까지 같습니다. 켜고 끈 것을 같은 결정에서 비교하니 탐색 결정
  1,093개에서 다르게 고른 결정이 0이었고, 플레이아웃 값 차이는 최대 2e-6이었습니다. 결정이 바뀌지 않으므로 규칙대로 속도만 쟀고,
  사용자 결정으로 강도 대국은 하지 않았습니다.
- **시간.** 조용한 기계에서 4스레드 탐색 결정당 1.28초 → 0.88초(비율 0.684 [0.675, 0.690]), Agent 턴 3.02초 → 2.02초. 효율 코어만 쓰게
  해 느린 호스트를 흉내 내면 6.50초 → 3.74초(0.575)입니다. 모델이 차지하던 시간이 38%에서 14%로 줄어, 이제 남은 시간의 대부분은 엔진입니다.
- 사용자: "이거 반영한게 무조건 좋은거 아니야? 그럼 기본 옵션으로 무조건 들어가면 좋은게 아니야?" 그래서 기본으로 켰고, `::batch=off`로
  예전 경로를 씁니다. 플레이 서버들은 다음 코드 동기화 때 바뀝니다.

## 엔진 4차 (병합 `a47fd570`, 11월 11일)

E3 탐색 좌석 하나와 앱 AI 셋인 판을 재 보니 엔진이 좌석 시간의 71–72%를 쓰고, 그 시간은 한 곳에 몰리지 않고 퍼져 있었습니다.
[앞의 세 차례]({{< relref "devlog/2026-11-03-engine-speed.md" >}})처럼 보이는 것을 하나도 바꾸지 않는다는 조건으로 네 단계(같은 질문의
답 기억, 바뀐 필드만 검사, 할 일 없는 훅을 빨리 끝내기, 공개 좌석 보기 만들기)와 탐색 좌석의 기억 열쇠를 바꿨습니다.

| 측정 (조용한 창, ABBA 세 쌍) | 전 → 후 | 비율 |
| --- | --- | --- |
| 탐색 결정당, Uprising | 0.818 → 0.702초 | ×0.859 [0.854–0.862] |
| 탐색 결정당, 원판 | 0.651 → 0.568초 | ×0.872 [0.871–0.873] |
| 합법 행동 목록 | | 표준 ×0.862, 확장 ×0.871 |
| 앱 AI 판 | | ×0.96–0.97 |

단계마다 전체 엔진 관문을 돌려 360판 동일성, 인코딩, 카탈로그, 소크, 기보 2,000판, 저장본이 모두 같았고, master와 같은 판 9개에서 고른
수와 탐색 값이 같았습니다. 다른 도구(Codex)의 검토 여섯 차례에서 나온 지적은 모두 프로세스 안에서만 생기는 입력이었고 고쳤습니다.
이 작업은 관문 다섯 번(약 6 CPU시간)을 썼고, 그 뒤 사용자는 관문 규칙을 바꿨습니다. 결과가 그대로인 하위 단계는 빠른 관문(pytest·ruff·
mypy·동일성·인코딩)만, 전체 관문은 병합 후보에서 한 번, 엔진 이벤트·합법 목록·서버·화면이 그대로면 E2E는 병합 때 한 번입니다.

## 전체 pytest를 약하게 하지 않고 빠르게 (병합 `4cc6b2c6`)

원인은 수집이었습니다. 이 개발 환경은 모든 명령에 바이트코드 쓰기를 끄는 변수를 걸어, pytest의 assert 변환 캐시가 생기지 않았습니다.
그래서 `-n 8`의 worker 여덟이 실행마다 시험 모듈 443개를 각자 다시 변환했습니다(worker당 약 14초).

- 컨트롤러가 실행마다 한 번, 병렬로 변환해 pytest가 찾는 자리에 쓰고, 실행이 끝나면 지웁니다. 남는 캐시가 없어 낡은 캐시 문제가 생기지 않습니다.
- 새 작업 트리를 만들 때 설치한 패키지를 바이트코드로 컴파일합니다(약 2초).
- 같은 시드 판을 시험마다 다시 두던 곳 셋은 한 번만 둡니다.

`-n 8` 170.5초 → 134.4초(−21%), `-n 4` 211.0초 → 179.8초, 수집만 33.9초 → 9.7초입니다. 시험 ID는 master와 같고(새 시험 2개만 더함),
일부러 깬 코드 셋을 캐시를 쓰는 시험이 모두 잡았습니다. 무거운 시험을 기본 실행에서 빼면 더 빨라지지만, 빠른 관문에서 그 검사가 빠지므로
사용자는 하지 않기로 했습니다.

## 부하에서 깨지던 E2E 넷 (병합 `6816ef72`)

`pytest -n 8`을 옆에서 돌리며 수정 전 스크립트를 다섯 번씩 돌려 재현했습니다.

- `vp_ledger`: 기록 줄 표시가 2.5초 뒤 꺼지는데, 부하에서 사진 응답이 그보다 늦어 꺼진 뒤를 쟀습니다. 페이지 시계를 세우고 "요청한 사진이
  모두 답을 받음"을 기다립니다.
- `table_motion`: 진짜 화면 결함이었습니다. 부하에서 큐브 상자의 폭이 0으로 재여 미끄럼이 건너뛰어졌습니다. 이제 보드에 인쇄된 옛 레벨
  자리에서 미끄러집니다.
- `spectate`, `scouts_stage`: 고정 대기를 움직임이 멈출 때까지의 대기로 바꿨습니다.

수정 뒤 같은 조건에서 table_motion 3/5 → 5/5, vp_ledger 4/5 → 5/5였고, 세 브랜치를 합친 트리에서 E2E 87/87이 통과했습니다.

## 남은 점

- 묶어 읽기와 엔진 4차의 효과를 셀러론 PC에서는 아직 재지 않았습니다(묶어 읽기만 추정하면 0.6–0.75배).
- 아낀 시간을 세계 수로 쓰는 안(예: Agent 턴 24세계)은 수가 바뀌므로 따로 측정해야 합니다.
- 느린 실제 연결에서 사진이 2.5초보다 늦게 오면 기록 줄이 화면 밖으로 밀립니다(제품 동작으로 둠).
